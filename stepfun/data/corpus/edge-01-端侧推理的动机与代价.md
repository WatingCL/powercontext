# 端侧推理：为什么把计算留在浏览器

把模型放到用户设备上运行，最直接的理由是数据不出本机。以个人知识库为例，用户导入的往往是工作笔记、实验记录、合同草稿，这些内容一旦上传到云端做向量化，就等于把原文副本交给了服务方。端侧推理从结构上消除了这条数据路径，因为文本从未离开浏览器。

第二个理由是延迟。云端推理的一次往返包含排队、传输与序列化开销，在网络状况一般时，端到端延迟常常是本地推理的数倍。对于检索这类需要"边输入边出结果"的交互，本地推理能显著改善手感。

第三个理由是成本可分。服务端不需要为每个用户预留 GPU 算力，也不需要为向量化付费，边际成本接近于零。对独立开发者来说，这让"每个人都有自己的知识库"从口号变成可行的产品形态。

代价同样明确。第一是首次加载成本：模型文件从几十兆到几百兆，用户第一次打开页面需要等待下载与初始化。第二是设备差异：同一份代码在不同显卡、不同浏览器上的性能可能相差十倍。第三是能力上限：端侧只能跑小模型，语义表达能力不如云端大模型，需要用更好的检索策略来补偿。

工程上常见的缓解手段有三条。模型懒加载：先让界面可用，用户第一次触发导入或检索时再加载权重，并给出明确的进度。模型缓存：利用浏览器的 Cache Storage 或 IndexedDB 保存权重，第二次访问直接命中本地缓存。量化压缩：用 INT8 或 FP16 权重把体积降到原来的四分之一到二分之一，同时把推理后端切到更合适的执行器。

需要强调的是，端侧推理不等于"推理结果也留在本地"。如果应用把文本或向量发给服务端，端侧推理的隐私价值就打了折扣。真正符合端侧定义的实现是：原文与向量都留在本机，服务端最多只承担同步与备份，并且默认关闭。

最后一点是合规与可验证性。声称"本地推理"时，最好让用户能自证：界面上显示当前使用的推理后端与模型版本，提供网络面板无外部推理请求的截图，或者干脆把模型文件与推理代码一起提交。可验证的声明比口号更有说服力。
