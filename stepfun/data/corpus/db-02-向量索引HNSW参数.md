# 向量索引：HNSW 的参数与召回

精确的近邻检索需要把查询向量与库中每个向量逐一比较，代价随数据量线性增长。HNSW（分层可导航小世界图）用图结构把检索复杂度降到近似对数级，因此成为向量数据库的默认选择。

它的结构可以理解为多层图：最底层包含所有节点，越往上节点越稀疏，顶层只有少数"枢纽"。检索从顶层入口点开始，在每一层做贪心搜索逼近查询向量，然后下降一层继续，直到最底层得到候选集。这种"先粗后细"的策略让它在大规模数据上仍能保持较低延迟。

影响效果与性能的参数主要有四个。m 控制每个节点的出边数量，越大图越密，召回越高但内存占用与构建时间上升。ef_construction 控制建图时的候选队列长度，影响图的质量。ef_search 控制检索时的候选队列长度，是最常调整的在线参数：调大能提升召回，代价是延迟线性增加。distance 决定度量方式，余弦距离适合已归一化的文本向量，内积适合未归一化的场景。

工程上常见的误区是把"高召回"当成唯一目标。实际系统里，召回从百分之九十五提升到百分之九十九，延迟可能翻倍，而用户几乎感知不到差异。更合理的做法是先确定可接受的端到端延迟预算，再在这个预算内调 ef_search，用离线评测集测出召回曲线，选一个性价比拐点。

另一个误区是忽略索引与写入的关系。HNSW 是增量可构建的，但新写入的节点需要一定时间才能被检索到，具体表现取决于索引的刷新策略。对"导入后立刻要能搜到"的产品，必须在写入后显式触发刷新，并把刷新耗时计入导入的端到端时间，否则用户会看到"刚导入却搜不到"的怪现象。

还有一点容易被忽略：向量维度对内存的影响是线性的。三百八十四维与七百六十八维，同样条数下内存占用差一倍。端侧或嵌入式部署时内存往往是硬约束，选模型时要把维度当成成本项一起考虑，而不是只看检索质量。

最后，度量方式必须与产生向量的模型匹配。用余弦距离检索已做 L2 归一化的向量，等价于内积排序，两者结果一致；但如果向量未归一化又用余弦，实际排序会被长度信息干扰，表现为"短文本总是排在前面"这类难以解释的现象。
