# 增量写入、索引刷新与会话状态

知识库类应用的写入模式与传统的批量导入不同：用户会不断追加文档，每次只导入几篇，且期望导入完成后立刻能检索到。这要求数据层同时满足三个条件：写入幂等、索引及时可见、集合状态隔离。

写入幂等靠主键设计实现。每个文本块应当有一个由"文档标识 + 块序号 + 内容摘要"推导出的稳定主键，这样同一篇文档重复导入时，落库操作变成覆盖而不是追加。缺少这一层设计，用户反复点击导入会让库里出现大量重复块，检索结果里同一段文字反复出现，看起来像是排序出了问题。

索引及时可见靠显式刷新实现。数据库侧的向量索引与全文索引在后台异步构建，写入成功不等于可检索。常见的做法是在一批写入完成后调用一次刷新，再返回给前端"新增 N 块，当前共 M 块"的确认。刷新的耗时与批量大小相关，应当单独计时并在界面上体现，这样用户能理解"导入慢在哪儿"。

批量大小是另一个影响体验的参数。逐条写入会产生大量往返开销，整批写入则可能触发单语句大小限制，且失败时需要整体回滚。工程上常用三十二到一百条一批的折中，并在批与批之间让出事件循环，让进度条能刷新。对端侧向量化来说，批大小还影响推理吞吐：批太小，GPU 并行度不足；批太大，单次等待时间变长，用户感知为"卡住"。

集合状态隔离常被低估。当应用支持多个知识库时，必须保证检索只发生在当前集合内，切换集合后结果不串。实现上有两种方式：一是每个集合一张表，检索时表名由集合名派生；二是单表加集合标识列，检索时带过滤条件。前者隔离彻底、实现简单，缺点是集合数量多时表数量膨胀；后者便于做跨集合检索，但每个查询都要带过滤，且删除集合需要清理数据。

会话状态还包括"当前选中哪个集合"。这属于用户偏好，存在浏览器本地即可，刷新页面后恢复。但如果要在多设备间同步，就需要服务端持久化，并处理并发修改的冲突。

最后是删除语义。删除集合应当同时删除索引与元数据，避免留下无法访问的孤立表；删除单篇文档则需要按文档标识删除所有块，并触发一次刷新。这两种删除都应当有确认步骤，因为知识库的误删成本通常高于误建。
