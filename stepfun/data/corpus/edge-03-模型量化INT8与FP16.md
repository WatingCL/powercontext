# 模型量化：INT8 与 FP16 的取舍

量化是把模型权重从高精度浮点映射到低精度表示的过程。对端侧部署而言，它同时解决三个问题：文件体积、内存占用、推理速度。

FP16 是最保守的方案。它把 32 位浮点换成 16 位浮点，数值范围与精度都保留了足够余量，几乎不需要校准，转换过程通常是逐层做类型转换。体积压缩比为 2 倍，在支持半精度运算的硬件上（例如多数桌面显卡的 WebGPU 后端）速度也有提升。缺点是它只压缩了一半体积，对网络带宽不敏感的场景收益一般。

INT8 是压缩效果更明显的方案。把权重映射到 8 位整数，体积压缩比接近 4 倍。主流的实现是动态量化：在校准阶段统计每一层权重的分布，选取缩放系数，推理时把整数权重反量化成浮点参与计算，激活值仍然保持浮点。这样做的好处是不需要准备校准数据集，实现简单，精度损失通常在可接受范围内；代价是反量化带来额外开销，实际加速比不如"整型推理"，在 CPU 上主要赚到的是带宽与缓存命中。

对 embedding 模型来说，量化最需要关注的是表示空间的稳定性。检索依赖于向量之间的相对距离，只要量化后的向量保持了原有的方向与相对关系，下游的排序质量就不会明显下降。因此评估量化损失时，除了看任务指标（召回率、排序质量），还应该看向量层面的保真度：同一批文本在量化前后生成向量的余弦相似度均值，以及量化后 Top-K 检索结果与量化前的重叠比例。这两个指标比单一的准确率更能说明"到底损失在哪儿"。

实践中还有两个细节值得注意。第一，量化后要统一做 L2 归一化，否则缩放系数的偏置会被余弦距离放大。第二，不同文本长度的受损程度不同：长文本的池化会平均掉量化噪声，短查询更敏感，因此查询侧量化损失往往大于文档侧，评估时必须把两者分开统计。

最后是报告规范。要给出量化前后的实际文件体积、压缩比公式、评测集与指标，并说明量化是用官方发布的权重还是自行转换的。如果自行转换，应附上转换脚本与依赖版本；如果用官方权重，也应说明其量化方法，避免让人误以为是自己做的。
