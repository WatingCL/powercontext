# WebGPU 与 WASM：推理后端怎么选

在浏览器里执行神经网络推理，目前有两条成熟路线：WebGPU 与 WebAssembly（通常配合 SIMD 与多线程）。

WebGPU 把计算图映射到显卡，适合矩阵乘密集的模型。对 embedding 这类小模型，WebGPU 的优势主要体现在批量吞吐上：一次编码几十条文本时，GPU 的并行度被充分利用，单位时间处理的文本数往往是 CPU 的数倍。但单条短文本的推理未必更快，因为存在内核调度与数据传输的固定开销，冷启动时的着色器编译也可能带来明显的一次性延迟。

WASM 走 CPU 执行，兼容性最好。只要浏览器支持 WebAssembly，推理就能跑起来，不依赖显卡驱动。它的短板是吞吐较低，长文本或大批量时耗时明显上升。不过在单条查询编码这种"小输入、低延迟"的场景下，WASM 与 WebGPU 的差距会缩小，因为 GPU 的固定开销占比变大。

正确的做法是运行时探测、自动选择并显式提示。探测顺序一般是：先检查 navigator.gpu 是否存在，再调用 requestAdapter 请求适配器，成功后再尝试初始化会话。任何一个环节失败，都要能回落到 WASM，而不是让页面停在加载状态。

这里有几个容易踩的坑。第一，存在 navigator.gpu 不等于可用，有些环境里对象存在但 requestAdapter 返回空。第二，适配器可用不等于模型能跑，某些算子在某些后端上没有实现，会退化或直接报错，因此首次推理要放在异常处理里，并准备回退路径。第三，WebGPU 的会话初始化是异步的，UI 上必须有中间状态，否则用户会以为页面卡死。

界面上至少要展示三样东西：当前后端（WebGPU 还是 WASM）、当前精度（FP16、INT8 或 FP32）、以及降级原因。降级原因尤其重要，它让用户知道自己看到的是哪条执行路径，也让评审能够复现。一个常见的做法是在页头放一个常驻徽标，鼠标悬停时显示适配器名称与选择理由。

如果要做性能对比，务必分别测量两条路径，并区分首次与预热后的结果。首次测量包含着色器编译与权重上传，往往比稳态慢一个数量级；只报首次结果会低估 WebGPU，只报预热结果则掩盖了用户体验。报告时把两者分开，并注明重复次数与所取分位数。
